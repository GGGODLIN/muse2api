## 新發現的風險

### 1. 高：參考圖欄位不只支援圖片，還能讀取 Mac 上的檔案，並發起 SSRF
**位置：`engine.py:940–1046`，`_normalize_image()`、`_attach_image()`。**

參考圖字串有兩條危險分支：以 HTTP／HTTPS 開頭，就由 Python 下載；否則只要 `os.path.isfile(img)` 成立，就直接 `open(img, "rb")` 讀取。沒有允許目錄、圖片內容驗證或下載大小上限，讀到的資料接著會送進 **Muse 網頁的檔案輸入流程**。

這代表能呼叫圖像／影片 API 的持鑰者，取得的不是單純「使用 Muse 額度」，還包含 muse2api 程序的本機檔案讀取能力。例如傳入專案內 `.env` 的實際路徑，就會走讀檔分支。**這不是未登入即可下載任意檔案，也不是直接把原始檔回傳給 API 呼叫者；我確認的是讀取與交付網頁的資料流，沒有實測 Muse 最終接受哪些檔案。**

HTTP 分支則沒有排除迴環、私有或 link-local 位址，也沒有逐次檢查重新導向目的地。服務只綁 `127.0.0.1`，不會限制它主動連到哪裡；單純檢查 URL 開頭也不足以防 SSRF。citeturn878667view4

**建議：必修。** 你的用途是文字 LLM 上游，最小做法是直接停用圖片、圖片編輯與影片路由。需要保留時，刪除本機路徑分支，優先只接受有大小限制、經實際解碼驗證的上傳圖片；遠端 URL 另做完整目的地與重新導向檢查。

### 2. 高：主引擎明確以 `--no-sandbox` 執行網際網路內容
**位置：`engine.py:57–83`；瀏覽器啟動參數。**

主引擎啟動 Chromium 時固定加上 `--no-sandbox`，再載入 Muse 網頁及它取得的內容。對直接在 Mac 上執行的情境，這是拿掉瀏覽器的重要隔離層；風險範圍不是只有那個新帳號，還涉及程序執行身分可存取的資源。

**這不是「網頁 JavaScript 現在就能任意執行 shell」的發現。** 它的問題是：一旦碰到可利用的瀏覽器漏洞，少了一道原本應存在的防線。

**建議：必修。** Mac 原生部署移除 `--no-sandbox`，用一般使用者執行，保留獨立 profile；不要把需要關沙盒才能運作當成正常部署條件。

### 3. 中：不同 API 請求會共用上游對話，造成跨任務資料與指令污染
**位置：`engine.py:273–313`、`829–890`，`reset_thread()`、`chat_stream()`。**

每次文字請求呼叫的是 `reset_thread(for_chat=True)`；在没有附件、卡住等條件，而且畫面氣泡數不到 16 時，它會直接沿用現有對話。判斷中**沒有下游 session 或 conversation 的識別**。

因此即使只有你一個人、一個 Muse 帳號，也可能是：「A 任務剛送完專案資料，B 任務接著在同一條 Muse 對話提問」。B 的輸入 JSON 沒有 A，不代表 Muse 看不到 A。先前任務中的惡意指令，也可能留到後續任務。

另外，重設失敗會被 `except Exception: pass` 吞掉，沒有「確認乾淨才可繼續」的保證。

**建議：接免費池前必修。** 每個獨立 API 請求建立新的上游對話，確認重設成功才送出；失敗就回錯，不要繼續沿用。先不要為省延遲實作跨請求對話重用。

### 4. 中：CDP 不驗證瀏覽器身分就接管，且放寬所有 WebSocket Origin
**位置：`engine.py:57–83`、`124–145`、`197–203`；`cdp.py:15–17`。**

CDP 是可控制瀏覽器、讀取 cookie 的除錯介面。`start()` 發現指定埠的 `/json/version` 有 `webSocketDebuggerUrl`，就直接連接，沒有核對它是否屬於自己啟動的程序或自己的 profile。隨後 `_open_page()` 會關閉該瀏覽器的所有 page，而 `_apply_cookies()` 會清除瀏覽器 cookie。

所以**接錯現有瀏覽器時，影響可以超過這個新 Muse 帳號**。此外，回應裡的 WebSocket URL 也直接受到信任，沒有目的地限制；啟動參數又包含 `--remote-allow-origins=*`。

需要區分：**我沒有證據說這個 CDP 埠綁在 `0.0.0.0`。** Chromium 原始碼的這條啟動路徑預設嘗試綁 `127.0.0.1`，再嘗試 `::1`；但那不是你實際執行程序的監聽實測。也不能只憑 Origin 萬用字元，就宣稱任意網站必然能完成接管。citeturn460212view3

**建議：要修。** 埠被未知程序占用就停止，不自動接管；只接受已確認屬於自己的程序／profile 與迴環 WebSocket URL。移除 Origin 萬用字元，配合 CDP client 調整連線方式。

### 5. 中：帳號標籤存在需要點擊觸發的儲存型 XSS
**位置：`admin.html:1061–1063`，改名與刪除按鈕。**

問題不是所有 `innerHTML` 都沒處理，而是這兩個按鈕把標籤放進 **JavaScript 字串**：

```html
onclick="renameAcc('${a.id}','${esc(a.label)}')"
```

`esc()` 做的是 HTML 編碼。瀏覽器解析屬性時會把引號字元實體還原，接著才把 `onclick` 當 JavaScript 編譯，因此不能保護裡面的 JavaScript 字串。隔離測試確認，特製標籤可讓點擊處理器執行額外的無害標記指令。HTML 與 JavaScript 語境需要不同處理，不能共用一種編碼。citeturn878667view1

前提是惡意標籤先被匯入或寫入，而且你點了相應按鈕。**不是一般上游文字回應一出現，就會自動執行。** 成功執行後則與管理頁同源，能取得頁面中的 Key 或呼叫管理 API。

**建議：要修，但不必重寫整個面板。** 拿掉這些動態 inline handler，用 `addEventListener` 傳遞標籤資料；不要把標籤拼成程式碼。

### 6. 中：下載兜底接受任意副檔名，再與管理面板同源提供
**位置：`engine.py:912–937`、`1048–1109`；`app.py:1271–1279`。**

正常抽取媒體的路徑會選擇有限的副檔名；但抽取失敗後，下載兜底只找下載目錄裡新增、非 `.crdownload`、大小大於零的檔案，**沒有驗證一定是圖片或影片**。搬到媒體目錄時還會保留下載檔的副檔名，最後由 `FileResponse` 提供。

因此，**假如兜底收進 HTML 或 SVG 等可執行內容**，使用者透過面板的「開啟」連結檢視它，就可能在管理頁同一個 origin 執行內容。這是條件式風險：我沒有實測 Muse 能否被誘導產出並下載這樣的檔案，不能當成已完成的攻擊鏈。

**建議：保留媒體功能才需要修。** 兜底也必須驗證檔案內容並限制類型，不信任下載副檔名；不允許的內容拒收，或強制附件下載，不能當管理站同源文件開啟。停用媒體功能可一起消除此路徑。

### 7. 中：串流取消可能留下永久持鎖的 worker，拖垮整条上游
**位置：`app.py:213–300`，`safe_chat_stream()`。**

worker 在持有全域生成鎖 `GEN_LOCK` 時，呼叫沒有 timeout 的 `q.put()`；佇列容量只有 100。當下游停止消費而佇列滿了，worker 會卡在 `put()` 裡，執行不到後面的停止旗標檢查。

把 `stop_event` 設為 true 不會喚醒這個阻塞。隔離測試確認這個機制：設置停止旗標後，worker 仍卡住、鎖仍被持有。Python 的阻塞式 `Queue.put()` 本來就會等到有空位，不會自動觀察另一個 Event。citeturn878667view2

所以原碼註解所說的「無論何時斷線都立即釋放、絕不死鎖」不成立。你的 relay 超時、取消或停止讀取，都是需要防守的正常情況。

**建議：接免費池前必修。** 所有佇列寫入都用短 timeout 並檢查取消，包含 error／done 通知；再限制等候請求數與取得生成鎖的時間。只加 `finally`，無法解決卡在 `put()` 的問題。

### 8. 中：匯入後重新注入 cookie，沒有保留原來的安全屬性
**位置：`engine.py:197–228`，`_apply_cookies()`。**

注入參數只有名稱、值、domain、path、`secure`、expires，沒有保留 `HttpOnly` 或原始 `SameSite`；也固定向 `.muse.ai` 與 `muse.ai` 注入，而不是保留原 cookie 的 host-only／domain 範圍。

重點是：**用擴充或 CDP 讀到 HttpOnly cookie，不代表重新注入後還保有 HttpOnly。** 這使原本應受保護的登入憑證，在被網站更新覆蓋前，可能以較弱的屬性存在。這不是所有網站都能讀取，但會放大 Muse 同源腳本或相關漏洞的影響。

**建議：要修。** 保留並還原 cookie 的安全屬性與原始網域範圍；最小做法至少是對確定屬於登入憑證的核心 cookie 明確設 `httpOnly=True`，不要任意擴大 domain。

### 9. 中：介面旋轉 Key 後，重啟可能讓舊 Key 復活
**位置：`app.py:1495–1503`；`config.py:11–29`。**

旋轉 Key 只修改當前 `CFG.api_key` 與 `.env`。但讀設定時，**既有程序環境變數優先於 `.env`**。

如果啟動器、shell 或 Compose 仍提供舊的 `MUSE2API_KEY`，重啟後就會重新使用舊 Key。這在你因 Key 洩漏而按「重新生成」時尤其容易誤判：畫面說舊 Key 已失效，卻不是跨重啟的保證。

**建議：使用介面旋轉功能就要修。** 設定只保留一個權威來源；或當 Key 由外部環境管理時禁止介面旋轉，明確要求修改啟動設定。驗收要包含「重啟後舊 Key 仍回 401」。

### 10. 低：帳號明文可接受，但 `.env` 權限與秘密副本要處理
**位置：`store.py:84–95`；`app.py:1506–1524`、啟動時產生 Key 的區段；`config.py` 的 profile／資料目錄設定；`tools/get_muse_cookie.py` 的上傳失敗處理。**

`accounts.json` 確實保存明文 cookie，但 `_write()` 使用 `tempfile.mkstemp()` 再原子替換，**不是直接以一般 `open()` 建立全員可讀檔案**；這種暫存檔預設只允許建立者讀寫。citeturn878667view3

真正漏掉的是 `_persist_env()`：它用一般 `open(".env.tmp", "w")` 再替換。在常見 `umask 022` 下，我的隔離測試看到原本 `0600` 的 `.env` 被替換成 `0644`；能否被其他使用者讀到，仍取決於父目錄權限。另有兩個秘密副本來源：自動產生 Key 會把完整 Key 寫進日誌；cookie 助手上傳失敗會把完整 cookie 印到終端。

瀏覽器登入狀態還留在 `~/muse2api-profiles/generate`，不只存在 `data/accounts.json`。實際 profile 檔案的權限、加密狀態與备份範圍，本次未實測。

**建議：明文帳號檔在你的情境可接受，不必先建加密儲存系統。** 把敏感目錄設為 `0700`、秘密檔設為 `0600`，讓 `.env` 寫入也使用安全暫存檔；停止自動把完整 Key／cookie 印進日誌或終端。

### 11. 低：CORS 設定看似可限縮，實際完全沒有使用
**位置：`app.py:57–75`；`config.py` 的 `cors_origins`。**

程式有解析 `MUSE2API_CORS_ORIGINS`，但 middleware 固定使用 `allow_origins=["*"]`，解析結果被丟在一旁。**只改環境變數不會收緊跨站來源。**

這不是獨立的 Bearer 驗證繞過：正常啟動、有強 Key 時，惡意網站不會因 CORS 全開就憑空知道 Key。因此在你的限制下列低，不列高。

**建議：順手修。** 本機 relay 不需要瀏覽器跨站呼叫，直接移除不需要的 CORS 開放；保留時才實際套用明確白名單。不要把 CORS 當成 API 授權替代品。

### 12. 低：鎖住 Git commit，還沒有鎖住完整執行環境
**位置：`requirements.txt:1–6`；`Dockerfile:1–27`。**

Python 依賴全部只有 `>=` 下限；Docker 使用可變 tag，安裝 Chromium 與 Python 套件時也沒有固定解析結果。所以同一份 commit 日後重建，可能得到不同依賴。這是可重現性與供應鏈範圍問題，**不是本次已確認某個安裝版本有漏洞**。

**建議：首次正式部署前補 lockfile／hash，記錄實際瀏覽器版本。** fork 不自動同步沒問題，但不要因此把瀏覽器安全更新也永久凍結。

## 我查過，但不認為需要報成新漏洞的部分

**一般媒體路徑穿越：未找到。** `app.py:1271–1279` 明確拒絕 `/`、`\`、`..`，而正常生成檔名使用 UUID。媒體目錄中預先放置 symlink 仍是可加固的情況，但我沒找到 API 能直接建立那個 symlink 的路徑，不把它報成遠端任意檔案讀取。

**除已知更新介面外，未找到新增的「無 Key 即可修改帳號」端點。** 沒有掛 auth 的還包括首頁／管理頁 HTML、健康檢查、媒體檔、cookie 助手、擴充下載與擴充檔名列表。公開靜態面板或工具原始碼，在你的本機情境可以接受；媒體若含敏感內容則不能把「知道隨機檔名才能下載」當成完整授權。管理與推論共用同一把 Key 是權限較大的設計，但只給自己的 relay 使用時，不必為此建立完整角色權限系統。

**沒有在已讀程式裡找到另一個隱藏的作者收件網址。** 動態網路路徑主要是參考圖下載、網頁 DOM 提供的媒體 URL，以及 CDP 回應提供的 WebSocket URL。這不等於實際執行時只會連固定幾個網域：Muse 網頁自身的網路活動，本次沒有抓包驗證。另要注意，這是本機**反代**，不是本機推論；`build_chat_prompt()` 會把傳入的系統設定、對話與工具結果送到 Muse，`store:false` 也沒有被實作成「不留下上游歷史」的保證。

## 已知三項修法的補洞

**刪更新功能的方向正確，但後端與前端要一起處理。** `admin.html:1307` 起有瀏覽器直連 GitHub 的備援檢查，頁尾還有定時呼叫；只刪後端端點或只藏按鈕不完整。**綁迴環要核對真正的啟動命令**：改 `config.py` 不會覆蓋 Dockerfile 中寫死的 Uvicorn `--host`；Docker 正確做法是宿主只發布 `127.0.0.1:18610:18610`，容器內仍可綁 `0.0.0.0`，原生 Mac 則明確讓 Uvicorn 綁 `127.0.0.1`。設定 Key 之外，建議把空 Key 時的 `auth()` 改成拒絕；原版正常 startup 會自動產生 Key，所以不是一般啟動就裸奔，但不應留下「startup 被跳過便全放行」的分支。**換成 cookie 助手不等於問題全消失**：它沒有主引擎的 `--no-sandbox`，但同樣會信任指定埠的 CDP，使用固定暫存 profile，還會在失敗時印出 cookie；應一併修正。保留擴充則除了縮 host permissions，也應固定上傳到你的迴環服務，移除從任意 `/admin` 頁面猜目的地的行為，並把 `popup.js` 的訊息輸出改成純文字。就你目前的用途，我建議先做**文字專用、獨立上游對話、受限 CDP、可靠取消**的最小版本，而不是先加更多治理層。
